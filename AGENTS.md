# Как работать с publisher-qa-lab

## Границы

- Локальные тесты работают со своим учебным сервисом на loopback. Они не доказывают поведение Site.pro и не требуют аккаунтов или ИИ в CI.
- Для Site.pro — только штатный UI своей учебной страницы, в согласованном объёме. Наблюдения записывай отдельно. Не переносить материалы EDU, учётные данные и сырые журналы в этот репозиторий.
- Ожидание брать из согласованного контракта или требования пользователя. Код, существующая проверка и наблюдение в UI — не источник нового требования. Если ожидаемое поведение не определено, сначала уточнить его.

## Куда смотреть

| Задача | Первая точка входа |
| --- | --- |
| Первая публикация, предпросмотр, переходы черновик → публичная версия | [Контракт пилота](docs/pilot.md#контракт), затем [карта рисков и тестов](docs/plan.md#риски-и-первый-пилот) |
| Повторная публикация, пропущенные поля, лимит формы | [Дополнительные контракты](docs/test-architecture.md#шесть-проверок-поверх-пилота), затем целевой spec |
| Куда добавить проверку и как выбрать слой | [Куда класть новый тест](docs/test-architecture.md#куда-класть-новый-тест) |
| Изоляция, POM, API и тестовые данные | [Архитектура набора](docs/test-architecture.md) |
| Site.pro | [Отдельный отчёт и ограничения](docs/sitepro-check.md) |

Читай только относящийся к задаче раздел, затем целевой spec и нужные импорты. Если точной ссылки нет, начни с ближайшего spec; отсутствие отдельного feature-context не блокирует работу.

## Изменения и проверки

- Выбирай минимальный слой: API для HTTP-контракта и подготовки, UI для пользовательского действия, свежий контекст посетителя для независимого чтения. Сохраняй сервер на тест и закрытие ресурсов при падении. POM и API не должны скрывать продуктовые ожидания; одинаковые проверки отображения допустимы в общем `expectContent`, ожидаемые данные остаются в spec.
- Для тестового кода: `npm run typecheck`, точечный непустой прогон (`npx playwright test <spec> --project=chromium --workers=1 --retries=0`). При изменении общих fixtures, сервиса или CI — также `npm test`; для жизненного цикла сервера — `npm run test:cleanup`. Настройка окружения — в [README](README.md).
- Не ослабляй ожидания ради зелёного прогона. Фиксируй точную команду и результат, отдельно помечай учебные сбои, контрольное падение и непройденные проверки. Временные следы и полные журналы не добавлять в Git.
- Значимые изменения контракта, тестовых ожиданий, изоляции, очистки, CI или этих инструкций отдавай на независимое ревью по [процессу](docs/reviewer.md), включая новые файлы. Не выдавай статическое ревью за runtime-прогон. Простые правки текста и уже принятый diff повторного ревью не требуют без нового сигнала.
