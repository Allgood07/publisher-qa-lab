# Reviewer eval: корпус и подсчёт

**Статус: подготовка.** Здесь восемь синтетических заданий и проверки подсчёта, не результаты модели. Примеры основаны на рисках Lab, но не запускаются против Site.pro, рабочего сервиса или внешней системы. Основной Playwright-набор и workflow не изменены.

## Проверить без модели

Из корня репозитория (Node.js ≥22.18):

```sh
node --test evals/reviewer/corpus.test.mjs evals/reviewer/score.test.mjs
```

Проверка не требует npm-зависимостей, ключей или браузера. Она проверяет четыре пары «дефект / корректное решение», исполняет парные контрпримеры, проверяет изоляцию входа и пересчитывает синтетические 24 попытки. Эту же команду можно добавить в CI отдельно от запуска модели.

## Провести ручной эксперимент после согласования бюджета

1. До запуска закрепить SHA корпуса, SHA-256 `prompt.md`, версию роли, точный идентификатор модели, UTC-дату, настройки генерации (в том числе явно недоступные), таймаут и предел токенов. Выбрать порядок восьми задач и три обхода, записать расписание заранее. Не подстраивать роль под итоговые задания: для калибровки использовать отдельный пример, например `examples/reviewer-mutation.test.mjs`.
2. На каждую попытку взять вывод `node evals/reviewer/task.mjs <task-id>` и передать **только этот вывод** в новую сессию без инструментов, доступа к репозиторию и автоматической подгрузки файлов. Не передавать ID, соседний пример, эталон или историю попыток. `contracts.json` содержит требования; `gold.json` и контрольные тесты видит только организатор/разметчик. Не давать Reviewer возможность прочитать этот README. Не повторять неудачный ответ вместо учёта таймаута или неверного формата.
3. Независимый разметчик сверяет место и механизм каждого замечания с `gold.json`: `match` с `defectId`, если совпали; `false-positive` для необоснованного замечания; `disputed` для возможной новой находки. К каждому добавляет `note` с объяснением. Две формулировки одного дефекта в попытке дают один TP. Спорное не считать подтверждённым TP/FP, пока не разобрано; эталон этой серии не переписывать. Сохранить очищенный ответ и разметку в порядке замечаний. Не сохранять ключи, сырые логи сессий или материалы рабочих проектов.

## Вход для подсчёта

`run.json`: объект `{ kind, metadata, attempts }`. Для эксперимента `kind` = `measured`, для искусственного примера `synthetic`. В `metadata`: `corpusSha` (40 hex), `promptSha256` (64 hex), `roleRevision`, `model`, `dateUtc` (`YYYY-MM-DDTHH:mm:ssZ`), непустой объект `sampling`, `tools: []`, `timeoutMs`, `maxOutputTokens` (положительные целые).

`attempts` содержит ровно 24 уникальные пары `taskId` и `attempt` (1–3). У валидной попытки `status: "ok"`, `response` в формате `prompt.md` и `labels` в том же порядке, что `findings` (пустой массив для `approve`). У `timeout` или `invalid` вместо ответа и разметки — `note` с причиной; для `invalid` здесь можно сохранить очищенный текст ответа. Пример записи:

```json
{
  "taskId": "q-1c8b",
  "attempt": 2,
  "status": "timeout",
  "note": "Лимит времени достигнут; валидного ответа нет."
}
```

```sh
node evals/reviewer/score.mjs run.json > reviewer-score.json
```

Вывод содержит строки по всем попыткам, суммарные TP/FN/FP, пропуски и ложные замечания по строкам, точность `TP/(TP+FP)` и полноту `TP/(TP+FN)`. Невалидные ответы и таймауты не считаются одобрением; на дефектном примере они дают FN. Доля блокировок корректного кода показана и среди всех его попыток, и среди валидных ответов. Повторяемость — тот же вердикт и тот же набор найденных дефектов во всех трёх валидных ответах; знаменатели — весь корпус и отдельно примеры с тремя валидными ответами. Повторяемость не означает правильность. Нулевой знаменатель выводится как `null`; спорные замечания помечают итог как `provisional`.

Результат пригоден для публикации только после ручной серии и разбора спорных замечаний. Даже 24 попытки — восемь примеров, а не репрезентативная оценка всех задач ревью.
