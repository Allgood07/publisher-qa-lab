# План publisher-qa-lab

## Цель и границы

Сделать самостоятельный портфолио-проект на TypeScript + Playwright и отдельно подготовить микро-страницу на Site.pro для отклика. Локальный сервис моделирует путь «черновик → предпросмотр → публикация → обновление». Это не копия Site.pro и не средство тестировать их внутренние интерфейсы.

На Site.pro — только штатные ручные проверки своей страницы: редактор, предпросмотр, публикация, видимость для обычного посетителя, ввод данных и адаптивность. Не проверяем чужие ресурсы и не используем внутренние API. Нагрузочные проверки исключены. В публичный репозиторий не попадают внутренние материалы EDU, данные аккаунтов, секреты и необработанные логи.

## Риски и первый пилот

| Риск | Приоритет | Где проверять |
| --- | --- | --- |
| Посетитель не видит опубликованный результат или видит неверную версию | Высокий | [`publish.spec.ts`](../tests/e2e/publish.spec.ts), [`publication-lifecycle.spec.ts`](../tests/e2e/publication-lifecycle.spec.ts) и [`publication-state.spec.ts`](../tests/api/publication-state.spec.ts); отдельное наблюдение на своей странице [Site.pro](sitepro-check.md) |
| Неопубликованная правка меняет публичную страницу | Высокий | [`published-snapshot.spec.ts`](../tests/e2e/published-snapshot.spec.ts); отдельно проверено на своей странице Site.pro |
| Невалидные данные сохраняются или валидные данные теряются | Высокий | [`draft-validation.spec.ts`](../tests/api/draft-validation.spec.ts), [`draft-validation-state.spec.ts`](../tests/integration/draft-validation-state.spec.ts), [`draft-text.spec.ts`](../tests/integration/draft-text.spec.ts) и [`draft-size.spec.ts`](../tests/integration/draft-size.spec.ts); на Site.pro [проверены поля редактора](sitepro-check.md#поля-редактора-и-текстовая-ссылка), форма посетителя не проверялась |
| Ссылки или контент недоступны на узком экране | Средний | [`narrow-publication.spec.ts`](../tests/integration/narrow-publication.spec.ts) — локально только контент; на своей странице Site.pro проверена одна внутренняя ссылка и контент при 360 px |

**Кандидат на пилот:** автор сохраняет черновик, сверяет предпросмотр и публикует страницу; независимый контекст посетителя видит согласованный заголовок и содержимое. Это предложение для локального контракта, не утверждение о Site.pro. До кода согласовать наблюдаемые результаты, исходное состояние, способ изоляции данных и проверку очистки. POM или фабрики добавлять только там, где они устраняют повторение или помогают владеть данными. Unit-тесты — только для собственной нетривиальной логики.

## Этапы и контрольные точки

Ориентир на расширенную версию: 22–28 часов. Не переходить к тиражированию тестов до прогона и ревью пилота.

1. **План и рамки.** Зафиксировать контракт локального сервиса и границы, получить независимое ревью плана.
2. **Site.pro.** Собрать страницу, пройти собственный маршрут вручную. Для подтверждённых дефектов записать окружение, предусловия, точные шаги, ожидаемый результат и его источник, фактический результат, повторяемость, влияние и очищенное доказательство. Если подтверждённых находок нет, не выдавать гипотезы за дефекты.
3. **Локальный пилот.** Реализовать минимальный сервис и один сценарий, выполнить целевой непустой прогон, записать команду, результаты и состояние тестовых данных. Ревью до расширения набора.
4. **Расширение и исправления.** Добавить проверки UI/API/интеграции по рискам. Настроить CI. Разобрать реальное падение или явно маркированный локальный учебный сбой; подтвердить исправление тем же целевым прогоном, не ослабляя проверку.
5. **Независимая проверка и публикация.** Проверить запуск из чистого клона, исправить замечания и перепроверить изменения. Очистить доказательства перед публикацией. Проверить Site.pro и ссылки без входа. В отклик — URL страницы между `<круто>` и `</круто>`.

## Роли Codex

Определения под этот проект находятся в [`.codex/agents/`](../.codex/agents/); [очищенная запись реальных вызовов](codex-roles.md) относится к отдельному учебному сценарию, не к историческому прогону пилота. Planner связывает риски и ожидаемые результаты; Architect принимает конкретное решение по архитектуре и изоляции; Generator реализует и прогоняет пилот; Healer разбирает отказ по первичным данным; Reviewer даёт независимое заключение без правок. Оркестратор вызывает только нужную роль, передаёт scope и критерии, принимает решение о следующем шаге. Определения ролей сами по себе не доказывают запуск: для портфолио сохранить очищенную запись фактических вызовов, входов, результатов и решений. Тесты запускаются без агентского инструмента.

## Критерий готовности

По README из чистого клона можно запустить заявленные локальные проверки, увидеть отчёт и отличить подтверждённый результат от ограничения. Для ручных находок есть отдельные воспроизводимые шаги. Пропуски, неподтверждённые выводы и учебные сбои явно обозначены.
