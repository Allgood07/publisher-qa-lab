# Сохранение черновика при конфликте версий

Это контракт локального Publisher QA Lab, не описание Site.pro. База работы: `47fca0f`.

- `GET /editor` сообщает текущую ревизию заголовком `X-Draft-Revision`; форма отправляет её в скрытом поле `baseRevision`. Первая ревизия — `0`, счётчик увеличивается при каждом успешном сохранении, не при публикации. Токен относится к одному процессу: состояния после рестарта нет.
- `POST /draft` с текущей ревизией сохраняет оба поля и возвращает `303 /editor?notice=saved`. С устаревшей или иной несовпадающей корректной ревизией — `409`: черновик, его ревизия и опубликованный снимок не меняются. Сравнение и запись выполняются без промежуточного ожидания.
- При конфликте редактор явно сообщает, что сохранения не было, показывает оба введённых поля и даёт открыть свежий черновик в новой вкладке. Автор переносит правку вручную. Из экрана конфликта нельзя сохранить или опубликовать; автоматического слияния нет.
- Старый запрос без `baseRevision` по-прежнему сохраняет безусловно и увеличивает ревизию; такая запись не защищена от перезаписи. Если поле передано, оно должно встретиться ровно один раз и содержать неотрицательное целое в десятичной записи без ведущих нулей (кроме `0`); иначе `400`. Сохраняются проверка обязательных полей и лимит всего закодированного тела в `16 384` байта.

Выбор слоя: [HTTP-spec](../tests/api/draft-revision.spec.ts) проверяет статус и состояние после отказа без браузера. [UI-сценарий](../tests/e2e/draft-conflict.spec.ts) проверяет предупреждение, введённый текст, восстановление через новую вкладку и оба поля у независимого гостя до и после публикации. Начальное состояние создаётся через API. Условие на ревизию действует на сохранение, не на `POST /publish`: публикация по-прежнему копирует текущий сохранённый черновик.

## Локальная приёмка

- `npm run typecheck` — успешно.
- `npx --no-install playwright test tests/api/draft-revision.spec.ts tests/e2e/draft-conflict.spec.ts --project=chromium --workers=1 --retries=0 --reporter=list` — 3 passed. Если выбрать только API-spec и задать `PLAYWRIGHT_BROWSERS_PATH` на пустой каталог — 2 passed.
- `npm test` — 19 passed. `npm run test:cleanup` распознал ожидаемое падение и подтвердил остановку по PID и TCP.

**Контрольные прогоны на копии.** Когда отключено только сравнение ревизий, API получает `303` вместо `409`, а UI не показывает предупреждение; оба теста конфликта падают. Независимый Reviewer указал второе ложное прохождение: прежние проверки пропускали V2, если выводить её рядом с корректной V1. В копии с таким поведением до усиления прошло 3/3, после проверки отсутствия обоих полей V2 в HTML и на экране упали оба теста конфликта. Это намеренно внесённые изменения в копии, не дефекты Site.pro и не результат CI.

**Решение о приёмке.** Первую версию тестов не приняли: зелёный результат не исключал показ V2 рядом с V1. После проверки замечания на контрольной копии усилили ожидания, повторили локальные прогоны и передали весь diff на повторное read-only ревью. Reviewer снял блокер статически; команды выполнил отдельно исполнитель. Владелец открыл [PR #1](https://github.com/Allgood07/publisher-qa-lab/pull/1/files) и влил изменение в `main` на `93ce1d3`.

**Воспроизводимые доказательства на `93ce1d3`:** [API-тест ревизии](https://github.com/Allgood07/publisher-qa-lab/blob/93ce1d38a82fd2f912e3ee1e2615c7799b48d286/tests/api/draft-revision.spec.ts), [браузерный сценарий конфликта](https://github.com/Allgood07/publisher-qa-lab/blob/93ce1d38a82fd2f912e3ee1e2615c7799b48d286/tests/e2e/draft-conflict.spec.ts) и [успешный QA-прогон после мержа](https://github.com/Allgood07/publisher-qa-lab/actions/runs/45813147954).
