# Локальный контракт и первый Playwright-пилот

**Статус:** контракт согласован, один сценарий реализован и проверен в Chromium. Результаты относятся только к учебному сервису, не к Site.pro.

## Контракт

Одна страница с фиксированным идентификатором `pilot-page`. Данные страницы — заголовок и основной текст; оба отображаются как текст, без обработки HTML или Markdown. Сервис доступен только на loopback. «Автор» и «посетитель» обозначают сценарии использования, а не уровни доступа: вход и контроль доступа за рамками пилота. Изоляция контекстов доказывает, что публичное представление не зависит от состояния браузера автора, но не доказывает конфиденциальность черновика.

| Действие | Наблюдаемый результат | Состояние после действия |
| --- | --- | --- |
| Открыть `/editor` на свежем сервере | Пустые поля «Заголовок» и «Текст». Прямой запрос к `/p/pilot-page` возвращает HTTP 404. | Черновика и опубликованной версии нет. |
| Ввести валидные значения и нажать «Сохранить черновик» | Появляется подтверждение «Черновик сохранён»; после перезагрузки редактор показывает те же значения. | Черновик сохранён на сервере; опубликованной версии всё ещё нет. |
| Открыть `/preview` через «Предпросмотр» | Видны метка «Предпросмотр» и точные заголовок и текст последнего сохранённого черновика. Прямой переход посетителя на `/p/pilot-page` всё ещё возвращает HTTP 404. | Предпросмотр не меняет данные. |
| Вернуться в редактор и нажать «Опубликовать» | Появляется подтверждение «Опубликовано» и ссылка на `/p/pilot-page`. | Сервер копирует сохранённый черновик в отдельный опубликованный снимок; черновик остаётся. |
| Перейти по публичному адресу в контексте посетителя | HTTP 200; основной заголовок и текст в основной области совпадают с ожидаемыми значениями; метки «Предпросмотр» нет. | Чтение не меняет данные. |

Для дальнейшего расширения: сохранение новой правки меняет только черновик; публичная страница показывает прежний снимок до повторной публикации. Пилот не проверяет этот переход, валидацию, публикацию несохранённых изменений, узкие экраны и параллельное редактирование.

## Один тест: «Публикация черновика видна посетителю»

1. Автор открывает редактор в стандартном контексте Playwright. Для посетителя создаётся отдельный чистый браузерный контекст без `storageState` автора. Посетитель открывает публичный URL напрямую и проверяет HTTP 404; автор проверяет пустые поля.
2. Автор сохраняет черновик с заголовком `Весенний выпуск` и текстом `Материалы номера уже готовы.` Проверяет подтверждение, перезагружает редактор и сверяет оба поля.
3. Автор открывает предпросмотр и сверяет метку, заголовок и текст с фиксированными данными теста. Посетитель снова открывает публичный URL напрямую и проверяет HTTP 404.
4. Автор возвращается в редактор, публикует страницу и проверяет подтверждение и адрес ссылки. Посетитель вновь открывает публичный URL напрямую и проверяет HTTP 200, точный заголовок и текст, отсутствие метки предпросмотра. Публичная страница сравнивается с данными теста, а не только с предпросмотром: оба экрана могут ошибаться одинаково.

Действия автора выполняются через UI. Для элементов использовать роли и подписи, для HTTP-статуса — ответ навигации, для ожиданий — штатные проверки Playwright, без фиксированных задержек. Падение должно указывать этап и несовпавшее ожидание.

## Изоляция, очистка и точечный прогон

- Один Chromium, один воркер, без повторов при падении. Каждый тест запускает отдельный процесс сервиса с пустым хранилищем в памяти. Сервис слушает на `127.0.0.1:0`: система назначает порт при привязке сокета. После начала прослушивания сервис сообщает фактический порт; оба контекста используют этот адрес. Записать PID дочернего процесса и назначенный порт. Не переиспользовать работающий сервер. Пилот не обещает сохранность данных после рестарта.
- Контекст посетителя закрывается при завершении теста, в том числе при падении. Playwright останавливает выделенный процесс и дожидается его завершения при штатном выходе и при падении проверки. Не добавлять HTTP-метод сброса ради теста.
- Целевой запуск: `npx playwright test tests/publish.spec.ts --project=chromium --workers=1 --retries=0`. Критерий: выбран ровно один тест, он прошёл с первой попытки, нет пропусков, код выхода 0.
- Отдельная проверка очистки: после сохранения черновика и подтверждения, что сервер отвечает на записанном порту, намеренно уронить проверку. Убедиться, что Playwright завершился с ненулевым кодом именно из-за контрольного падения. После выхода раннера внешняя проверка должна в течение 5 секунд подтвердить, что процесс с записанным PID завершился и TCP-подключение к `127.0.0.1:<порт>` отклоняется; HTTP 404 не считается признаком остановки. Затем повторить штатную команду: с тем же идентификатором страницы тест снова должен начать с пустых полей и HTTP 404. Зафиксировать фактические команды и результаты, контрольное падение записать отдельно от результата пилота.

## Результат прогона

macOS arm64, Node.js 26.13.1, Playwright 1.64.1, управляемый Playwright Chromium. Подготовка окружения и итоговый прогон:

| Команда | Результат |
| --- | --- |
| `npm ci --offline --no-audit --no-fund`, `npm run typecheck`, `npx playwright install chromium` | Зависимости переустановлены из кэша по lockfile, проверка типов прошла, Chromium доступен. Проверка из чистого клона на другой машине не выполнялась. |
| `npx playwright test tests/publish.spec.ts --project=chromium --workers=1 --retries=0` | `1 passed`, код 0, без пропусков; первый процесс PID 26316, порт 50465. |
| `npm run test:cleanup` | Отдельное намеренное падение после успешного сохранения и перезагрузки редактора (HTTP 200): `1 failed`, код Playwright 1 и маркер `PILOT_CONTROLLED_FAILURE`. Внешняя проверка подтвердила завершение PID 26335 и `ECONNREFUSED` на порту 50481 в установленный срок; код внешней проверки 0. |
| Повтор точно той же штатной команды | `1 passed`, код 0, без пропусков; PID 26359, порт 50491. С тем же `pilot-page` получены пустые поля и HTTP 404 до публикации. После выхода отдельно подтверждены завершение PID и `ECONNREFUSED`. |

Независимое ревью реализации в отдельных сессиях Pi: текст теперь сравнивается без нормализации пробелов, отсутствие метки проверяется по всей публичной странице. Замечание о строгом дедлайне закрыто: поздний `ECONNREFUSED` не засчитывается. Ревью статическое, прогоны выполнил автор пилота. HTML-отчёт штатного прогона хранится локально в `playwright-report/`.

## Отдельная проверка опубликованной версии

`tests/published-snapshot.spec.ts` проверяет следующий риск, не расширяя сценарий первой публикации. Автор публикует V1, а посетитель подтверждает HTTP 200 и точный заголовок и текст V1. Автор сохраняет V2 без публикации, перезагружает редактор и видит оба поля V2. Посетитель в новом контексте всё ещё получает HTTP 200 и точное содержимое V1. Повторная публикация V2 не входит в эту проверку.

- `npx playwright test tests/published-snapshot.spec.ts --project=chromium --workers=1 --retries=0` — `1 passed` до и после контрольного эксперимента.
- **Учебный сбой:** во временной копии сервиса сохранение черновика намеренно заменяло уже опубликованную версию. Та же команда дала `1 failed` (код 1) на последнем шаге: ожидалось `Весенний выпуск`, получено `Обновлённый выпуск`. Рабочий `src/server.ts` не менялся.
- `npm run test:cleanup` — контрольное падение пилота распознано, PID завершён, TCP-подключение отклонено. `npm test` после него — `2 passed` в одном воркере с отдельным сервером на тест.

## Контракт валидации черновика

`POST /draft` принимает поля `title` и `body` в форме. Если одно поле пустое или содержит только пробелы, ответ — HTTP 400 без перенаправления. Ранее сохранённый черновик и опубликованный снимок остаются неизменными. Проверка пустоты не должна нормализовать валидный ввод. Лимит размера и сообщения UI не входят в этот набор.

`tests/draft-validation.spec.ts`: четыре независимых API-случая изменяют только одно поле. Отдельный интеграционный тест публикует V1 и сохраняет V2 через штатные маршруты, проверяет исходное состояние, отправляет невалидную V3 и подтверждает, что редактор по-прежнему показывает оба поля V2, а новый посетитель — точное содержимое V1. Проверка валидного текста вынесена в `tests/draft-text.spec.ts`.

`npm run typecheck` — успешно. `npx playwright test tests/draft-validation.spec.ts --project=chromium --workers=1 --retries=0` — `5 passed`. `npm test` — `7 passed`, включая прежние сценарии. Отдельная сессия Pi согласовала реализацию без блокеров; ревью было статическим. Неизменность данных проверяется для репрезентативной V3, а не для каждого из четырёх API-случаев.

## Валидный текст без потерь

`tests/draft-text.spec.ts` сохраняет черновик через API (HTTP 303), проверяет точные значения полей после нового GET редактора и сравнивает предпросмотр с входными данными. Кириллица, кавычки и `&` сохранены; `<em>` отображается буквально, не создавая соответствующий HTML-элемент. `textContent` проверяет исходный текст, `innerText` — сохранение двойного пробела в отображаемом абзаце.

- `npm run typecheck` — успешно; `npx playwright test tests/draft-text.spec.ts --project=chromium --workers=1 --retries=0` — `1 passed`; `npm test` — `8 passed`.
- **Учебный сбой:** во временной копии абзац содержал вложенный `span` с `white-space: normal`. Исходный `textContent` остался прежним, но проверка `innerText` обнаружила один пробел вместо двух: `1 failed`, код 1. Рабочий сервис не менялся.
- Первое независимое ревью обнаружило, что проверка CSS родительского абзаца могла пропустить такое схлопывание. После перехода на точное сравнение `innerText` повторное ревью подтвердило снятие блокера.

## Публичная страница при ширине 360 px

`tests/narrow-publication.spec.ts`: данные с длинными фрагментами без пробелов в заголовке и абзаце публикуются через локальный API. Посетитель в мобильной эмуляции Chromium открывает штатный публичный URL и получает HTTP 200. Проверяются точный видимый текст, фактическая ширина области вёрстки 360 CSS px, отсутствие горизонтального переполнения документа и горизонтальные границы текста с учётом обрезающих предков. Для дробных координат текста допускается отклонение до 1 CSS px от округлённых границ. Вертикальная прокрутка допустима. Ссылки не входят в локальный контракт, реальные устройства и другие браузеры не проверялись.

- **Обнаруженный локальный дефект:** `npx playwright test tests/narrow-publication.spec.ts --project=chromium --workers=1 --retries=0` до исправления дала `1 failed`, код 1; область вёрстки 360 px, ширина прокрутки 772 px. Исходный trace сохранён локально (вне Git): `.cache/qa-evidence/narrow-publication-before.zip`.
- **Исправление:** `src/server.ts` применяет `overflow-wrap: anywhere` к статье, не меняя её текст и не скрывая переполнение. Повтор той же команды без изменения теста — `1 passed`.
- Независимое ревью выявило пробел в проверке обрезающих предков. После его исправления временная копия с `overflow: hidden` дала ожидаемое `1 failed` на проверке границы заголовка, хотя горизонтального переполнения документа не было. Повторное ревью сняло блокер. `npm run typecheck` — успешно, финальный целевой прогон — `1 passed`, `npm test` — `9 passed`.

У шагов минимум прав (`contents: read`); официальные actions закреплены полными SHA. Отчёт загружается после успеха или падения Playwright, если был создан. ## Вопросы, рассмотренные на ревью плана

- Достаточны ли HTTP 404 после предпросмотра и HTTP 200 после публикации, чтобы принять пилот, или проверка обновления черновика после публикации нужна уже в первом тесте? Предложение: вынести обновление в следующий тест, чтобы отдельно диагностировать два риска.
- Подходит ли модель «одна страница, хранилище в памяти, без авторизации» для первого пилота? Если нужна долговечность после рестарта или закрытый предпросмотр, согласовать это до реализации: текущий сценарий этого не доказывает.
- Принимаем ли правило «публикуется последняя сохранённая версия»? Поведение кнопки при несохранённых изменениях и правила невалидного ввода согласовать перед соответствующими проверками; пилот использует только сохранённые валидные значения.
- Достаточно ли проверки закрытия порта и повторного чистого запуска для выбранной изоляции? Если нет, указать, какой наблюдаемый признак очистки требуется.

Ревью подтвердило, что один тест покрывает риск неверной или недоступной первой публикации. Модель без авторизации и сохранности после рестарта принята. Обновление опубликованного снимка, несохранённые правки, валидация и адаптивность остаются за рамками пилота. Критерий очистки согласован после уточнения проверки PID и TCP-порта.
