# Роли Codex для publisher-qa-lab

Пользовательские сабагенты объявлены в [`.codex/agents/`](../.codex/agents/). Они не нужны для `npm test` и не подменяют отдельное [ревью Pi](reviewer.md).

| Роль | Вход | Результат |
| --- | --- | --- |
| [`planner`](../.codex/agents/planner.toml) | Риск, источник ожидаемого поведения, границы | Наблюдаемый сценарий, данные и критерий успеха |
| [`architect`](../.codex/agents/architect.toml) | Согласованный сценарий, стек и ограничения | Минимальный слой теста, изоляция, точечная команда |
| [`generator`](../.codex/agents/generator.toml) | Сценарий и разрешённые пути | Проверка, фактический прогон и его результат |
| [`healer`](../.codex/agents/healer.toml) | Первичные данные о падении и разрешённая правка | Разбор причины, минимальная правка, повтор той же команды |
| [`reviewer`](../.codex/agents/reviewer.toml) | Контракт, изменения и отделённые от вывода команды | Независимый вердикт и блокеры без правок |

Оркестратор выбирает только нужные роли и передаёт им объём и критерии. `healer` вызывается при конкретном падении, а не на каждый зелёный прогон. Для независимого ревью запускать новый `codex exec` с `-s read-only` и без истории реализации. Инструкция роли не заменяет песочницу: сабагенты наследуют права родительской сессии. `workspace-write` не ограничивает запись одним разрешённым файлом: это граница задания, которую проверяет оркестратор. `read-only` запрещает запись в рабочую область, но не отключает инструменты чтения.

## Фактический учебный прогон

Codex CLI **0.172.0** через `npx --yes --package=@openai/codex@0.172.0 -- codex`, macOS, Node.js 26.13.1. Упражнение выполнялось в отдельном временном Git-проекте с копией определений ролей. Работа с кодом — `codex exec --enable multi_agent_v2 --json -s workspace-write`; для каждого из двух ревью отдельный родительский `codex exec` с `-s read-only` вызвал одного дочернего `reviewer`. Доверие включалось только для временного проекта в изолированной конфигурации. Сырые журналы и данные входа в репозиторий не добавлены. Первая попытка без доверия не загрузила проектные роли; её не засчитываем.

**Вход:** модуль `exercise/publication.mjs` с `createPublisher()`, `saveDraft`, `publish`, `publicView`. После первой публикации гость должен видеть V1, после сохранения V2 — всё ещё V1, после повторной публикации — V2. Начальный модуль намеренно использовал `published ??= { ...draft }` и не обновлял снимок. Это учебный сбой, не находка в `src/server.ts` или Site.pro.

Ниже — сокращённая запись проверяемого прогона. Имена и количество дочерних сессий сверены с журналом делегирования Codex; незажурналированная пробная сессия не входит в счёт. Результаты команды сверены с событиями исполнения, а красный и зелёный прогоны отдельно повторены на копиях автором.

| Вызов | Что сделано | Решение |
| --- | --- | --- |
| Planner (1) | Сформулировал три наблюдения V1 → V1 → V2 с разными заголовками и телом. | Передать контракт Architect. |
| Architect (1) | Выбрал один `node:test` со свежим `createPublisher()` и точной сверкой обоих полей на каждом переходе. | Дать Generator реализовать только тест. |
| Generator (1-й) | Создал `exercise/publication.test.mjs`. `node --test exercise/publication.test.mjs`: 1 тест, 1 падение, код 1. На последнем шаге ожидалась V2, осталась V1. | Вызвать Healer по этому расхождению. |
| Healer (1) | В учебном модуле заменил `??=` на `=`. Та же команда: 1 тест прошёл, код 0. SHA-256 теста совпал до и после правки. | Отдать фикс и доказательства на независимое ревью. |
| Reviewer (1-й) | Нашёл блокер: тест передавал те же объекты, с которыми сравнивал результат; изменение входа могло подменить ожидание. | Вернуть только тест Generator. |
| Generator (2-й) | Передал `saveDraft` копии ожидаемых объектов; модуль не изменился, все три сравнения остались. Та же команда: 1 прошёл, код 0. | Перепроверить и повторить ревью. |
| Reviewer (2-й) | Согласовал разделение входа и ожиданий; больше блокеров в учебном сценарии не нашёл. Оба ревью статические, тесты ревьюером не запускались. | Учебный прогон принят. |

До и после исправления учебного модуля исходный тест имел одинаковый SHA-256 `a74b5f55c858448e982b2c604e10c94a780997ac11edfcb3ac0481a2018bfd60`. Усиление теста произошло **позже**, по замечанию Reviewer. Автор отдельно проверил усиленный тест на исходном дефекте и исправленном модуле: соответственно `1 failed` и `1 passed`. В другой временной копии, где `saveDraft` неверно менял входной заголовок перед сохранением, старый тест проходил, усиленный падал. Рабочие `src/` и `tests/` не менялись; `npm run typecheck` и `npm test` (`9 passed`) выполнены отдельно.

## Проверить вывод Reviewer без ИИ

`node --test examples/reviewer-mutation.test.mjs` — локальная [реконструкция](../examples/reviewer-mutation.test.mjs), не исходный журнал сессии. Не нужны зависимости, модель и аккаунт. На исправной реализации обе проверки проходят. На одном и том же мутанте старая проверка ложно зелёная, а усиленная обнаруживает повреждённый заголовок. Третий тест ожидает именно этот assertion: зелёный итог демонстрации означает, что расхождение поймано, а не что мутант исправен.

## Как повторить упражнение

Создать отдельный временный Git-проект, скопировать в него `.codex/agents/`, не добавлять реальные данные или учётные файлы. Создать только `exercise/publication.mjs` с начальным состоянием:

```js
export function createPublisher() {
  let draft;
  let published;
  return {
    saveDraft(content) { draft = { ...content }; },
    publish() { if (draft) published ??= { ...draft }; }, // учебный сбой
    publicView() { return published && { ...published }; },
  };
}
```

В авторизованном Codex CLI запустить сессию `codex exec --enable multi_agent_v2 --json -s workspace-write -C <временный-проект> -`. При необходимости подтвердить доверие только к проверенному временному проекту: `--trust` сохраняет это решение в конфигурации Codex. Передать оркестратору контракт V1 → V1 → V2 и порядок Planner → Architect → Generator. Разрешить Generator создать только `exercise/publication.test.mjs` и запустить `node --test exercise/publication.test.mjs`. При ожидаемом падении передать Healer только учебный модуль и попросить повторить команду без изменения теста. Затем вызвать Reviewer в отдельной сессии `-s read-only` с двумя файлами, контрактом и наблюдениями. Сохранять только очищенную сводку, не полные логи.
